# StableX — Currency Exchange Comparison Demo

StableX is a demo-first currency exchange comparison application built with Node.js and Express. It allows users to compare estimated exchange offers for USDT, USDC, and NGN, review fees and estimated returns, select a provider, and check connectivity to Solana Devnet.

> **Important:** Exchange rates and provider offers are simulated. The application does not execute real exchanges, process payments, or transfer cryptocurrency.

## Features

- Compare estimated exchange offers between USDT, USDC, and NGN.
- View multiple demo providers ranked by estimated amount received.
- Display estimated exchange rates, gross amounts, fees, and processing times.
- Select a demo provider and record the selection.
- Expose REST API endpoints for health checks, currencies, quotes, selections, and Solana status.
- Check Solana Devnet connectivity using `@solana/web3.js`.
- Use a responsive browser interface.
- Configure the server and RPC endpoint using environment variables.

## Installation and Setup

### 1. Open the project directory

If the project is already on your computer, open a terminal in the `stablex` directory.

To clone a GitHub repository instead:

```bash
git clone <your-repository-url>
cd stablex
```

### 2. Install dependencies

```bash
npm install
```

If dependencies have not yet been added to the project, install them with:

```bash
npm install express dotenv @solana/web3.js@1.98.4
npm install --save-dev nodemon
```

### 3. Configure environment variables

Create a `.env` file in the project root:

```env
PORT=3000
SOLANA_RPC_URL=https://api.devnet.solana.com
```

- `PORT` sets the local server port.
- `SOLANA_RPC_URL` sets the Solana RPC endpoint.

Do not commit `.env` or secrets to a public repository.

### 4. Confirm the package scripts

Your `package.json` should include ES module support and these scripts. Preserve any other existing dependencies and settings.

```json
{
  "type": "module",
  "scripts": {
    "start": "node server.js",
    "dev": "nodemon server.js"
  }
}
```

### 5. Start the application

For normal execution:

```bash
npm start
```

For development with automatic restarts:

```bash
npm run dev
```

Open [http://localhost:3000] in your browser while the server is running.

## API Endpoints

| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/health` | Checks whether the application is running |
| `GET` | `/api/currencies` | Returns supported currencies |
| `GET` | `/api/quotes` | Returns calculated demo exchange offers |
| `POST` | `/api/selections` | Records a demo provider selection |
| `GET` | `/api/solana/status` | Checks Solana RPC connectivity |

### Compare exchange offers

Example request:

```http
GET /api/quotes?amount=100&from=USDT&to=NGN
```

Parameters:

- `amount` — amount to convert, such as `100`
- `from` — source currency, such as `USDT`
- `to` — target currency, such as `NGN`

You can also test the endpoint from a terminal:

```bash
curl "http://localhost:3000/api/quotes?amount=100&from=USDT&to=NGN"
```

The endpoint returns simulated provider offers with estimated rates, fees, gross amounts, and net amounts. The precise response structure depends on the implementation in `server.js` and `providers/demoProvider.js`.

### Record a provider selection

The frontend sends a `POST` request to `/api/selections` with a quote ID and exchange context. Use a valid quote ID returned by the quotes endpoint.

Example request body (illustrative only):

```json
{
  "quoteId": "demo-provider-a",
  "amount": 100,
  "from": "USDT",
  "to": "NGN"
}
```

The example quote ID may differ from the IDs generated by your application. Selections are stored in memory for demonstration purposes and may be lost when the server restarts.

### Check Solana connectivity

```http
GET /api/solana/status
```

The endpoint attempts to contact the configured Solana RPC endpoint and retrieve network information, such as the Solana version and current slot.

A successful response indicates RPC connectivity at the time of the request. It does **not** mean a token swap or blockchain transaction has occurred.

## Exchange Calculation Logic

The demo provider uses predefined exchange rates and provider-specific adjustment factors to produce comparable offers.

- **Gross amount:** estimated output before fees.
- **Estimated fee:** simulated provider or transaction fee.
- **Net amount:** estimated output after applicable fees.

Offers are sorted by estimated net amount so users can compare the demo results. These values are simulated and should not be used for actual financial decisions.

## Solana Integration

StableX uses `@solana/web3.js` to communicate with Solana Devnet. The current integration checks RPC connectivity and retrieves basic network information.

The current project does not implement:

- Wallet connection or wallet signing
- On-chain token swaps
- USDT or USDC token transfers
- Transaction submission or settlement
- Live exchange-provider integrations

These features would require additional implementation, verified token and network details, provider integrations, and appropriate security controls.

## Current Limitations

- Provider selections are stored in memory rather than a persistent database.
- No real financial transactions are executed.
- Solana integration is limited to RPC connectivity and basic network information.
- Live provider APIs and production-grade transaction handling are not implemented.

## VOVE ID sandbox KYB integration

StableX includes a VOVE ID sandbox KYB flow at `/kyb.html`.

### Configure the sandbox

Copy `.env.example` to `.env` and obtain the following sandbox values from the VOVE dashboard/account owner:

- `VOVE_ID_API_KEY` — server-side API key.
- `VOVE_ID_PUBLIC_KEY` — public key used to construct the hosted KYB session URL.
- `VOVE_ID_KYB_FLOW_ID` — optional flow ID selected for the test business jurisdiction.
- `VOVE_ID_WEBHOOK_SECRET` — webhook signing secret, after configuring the webhook endpoint.
- Keep `VOVE_ID_ENVIRONMENT=Sandbox` and `VOVE_ID_API_BASE_URL=https://api.voveid.net/v2` for testing.

Never commit `.env`, expose API keys in browser code, or send credentials in chat. The KYB create-case call is made by the Express backend using `POST /kyb/case`. The hosted session is returned to the browser only as a time-limited verification URL.

### Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/kyb/readiness` | Reports whether sandbox configuration is present |
| POST | `/api/kyb/cases` | Creates a KYB case with VOVE sandbox |
| GET | `/api/kyb/cases/:refId` | Reads the local in-memory case record |
| POST | `/api/kyb/webhook` | Receives signed VOVE KYB webhook events |

Configure the webhook URL in the VOVE dashboard as `https://YOUR_PUBLIC_HOST/api/kyb/webhook`. For local development, use a secure tunnel URL. Do not expose this endpoint without configuring and verifying the webhook signing secret.

### Important limitations

- This first provider integration implements KYB case creation and local status tracking. It does not yet implement VOVE's separate individual KYC SDK flow.
- Case records are held in memory and disappear when the server restarts.
- A created KYB case is not an approval. The business must complete the hosted flow, VOVE must process it, and the result must be reviewed.
- Use synthetic test business information and VOVE-approved sandbox test data only. Do not upload real people's identity documents for this learning demo.
- The webhook handler follows the signature format shown in VOVE's KYB integration guide. Confirm the exact header/signature format with the VOVE dashboard or support before relying on it outside sandbox testing.
- No money movement or transfer execution is enabled by this integration.

## Durable transfer management (prototype)

The PostgreSQL foundation now includes customer-scoped beneficiaries, transfer drafts, lifecycle events, provider event records and audit entries.

### Required server configuration

- `DATABASE_URL` — PostgreSQL/Neon connection string.
- `BENEFICIARY_ENCRYPTION_KEY` — base64-encoded 32-byte key used for AES-256-GCM encryption of beneficiary details. Generate locally with:
  ```bash
  node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
  ```
- `STABLEX_OPERATOR_TOKEN` — bearer token required for manual lifecycle transitions.
- `STABLEX_EVENT_INGESTION_TOKEN` — bearer token required for internal provider-event ingestion.

Keep all values in the local server environment. Back up the encryption key securely: beneficiary records cannot be decrypted if it is lost.

### API

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/transfers/beneficiaries` | Save encrypted beneficiary details |
| GET | `/api/transfers/beneficiaries?customerId=...` | Retrieve a customer's beneficiary records |
| POST | `/api/transfers` | Create a durable DRAFT (requires `Idempotency-Key` header) |
| GET | `/api/transfers?customerId=...` | List up to 100 customer transfers |
| GET | `/api/transfers/:id?customerId=...` | Retrieve one customer transfer |
| PATCH | `/api/transfers/:id/status` | Operator-authorized lifecycle transition |
| POST | `/api/transfers/provider-events` | Idempotently record an internally forwarded provider event |

Allowed transitions: `DRAFT → QUOTED → AWAITING_FUNDING → FUNDED → SETTLEMENT_PENDING → COMPLETED`, with permitted `FAILED` and `CANCELLED` paths. Every transfer creation and status change writes a transfer event and audit record in the same database transaction. Duplicate idempotency keys return the original transfer; reusing a key with a different request returns HTTP 409.

### Important security and integration boundaries

This is a local integration prototype, not a production customer API. The `customerId` field is currently a caller-supplied identifier, not an authenticated identity; do not expose these routes publicly until real authentication, authorization and tenant isolation are implemented. The operator and event-ingestion bearer tokens are prototype controls, not replacements for an identity provider or provider-specific webhook signature verification.

Beneficiary details are encrypted at rest and decrypted by these prototype read endpoints. The caller-supplied customerId is not authentication; do not expose these endpoints publicly. Provider events are stored idempotently but do not automatically advance transfer state. Provider-specific signature verification, event-to-transfer correlation, reconciliation and automated state transitions remain follow-up work.

No endpoint in this milestone collects funds, creates a Paytrie transaction, signs a blockchain transaction, sends a payout, or moves money. Manual lifecycle changes are records only.

## Customer accounts and authentication (prototype)

StableX now implements step 1 of the customer flow: real account creation with email/phone verification, personal or business account types, and password sign-in. The authenticated account ID doubles as the `customerId` used by transfers, wallets and compliance.

Configure in the server-side `.env` file:

- `ACCOUNTS_DEMO_CODE_DELIVERY` — when `true` (default), email/phone verification codes are returned in API responses and printed to the server log so the flow works without an email/SMS provider. Set to `false` and wire a real provider before any production use; codes are then only hashed and stored.
- `SESSION_TTL_HOURS` — lifetime of issued session tokens, default 72.

### API

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/auth/register` | Create a PERSONAL or BUSINESS account; issues verification codes |
| POST | `/api/auth/verify/email` | Confirm the 6-digit email code |
| POST | `/api/auth/verify/phone` | Confirm the 6-digit phone code (accounts with a phone) |
| POST | `/api/auth/resend` | Reissue a code; the previous code for that channel is invalidated |
| POST | `/api/auth/login` | Password sign-in; returns a Bearer session token |
| GET | `/api/auth/session` | Returns the signed-in account, verification state and compliance gate |
| POST | `/api/auth/logout` | Revokes the current session |

Example registration:

```json
{
  "email": "customer@example.com",
  "phone": "+2348012345678",
  "password": "correct-horse-7",
  "accountType": "PERSONAL",
  "fullName": "Ada Lovelace"
}
```

`BUSINESS` accounts additionally require `businessName`. An account becomes `ACTIVE` when the email is verified and, if a phone was provided, the phone is verified too. Signing in before verification returns HTTP 403 with the pending channels and the account ID.

### How it is secured

- Passwords use `scrypt` with a per-account random salt; hashes are never returned by any endpoint.
- Verification codes are 6 digits, hashed at rest, expire after 15 minutes, are single-use, lock after 5 failed attempts, and issuing a new code invalidates the old one.
- Sessions are opaque 32-byte tokens; only a SHA-256 hash is stored. `GET /api/auth/session` resolves the token to the account and includes the compliance gate status linking to step 2 (KYC for PERSONAL, KYB for BUSINESS).

### Important limitations

- With demo delivery enabled the verification code is visible in API responses and logs; that mode is for local testing only.
- There is no email/SMS provider integration yet, no rate limiting on register/login beyond the code attempt lock, and no password reset flow.
- Existing endpoints still accept a caller-supplied `customerId`; pass the authenticated `accountId` as the `customerId` and scope all reads to the session owner via the `requireAuth` middleware before exposing these routes publicly.
- Account records live in PostgreSQL and are subject to the same prototype boundaries as the rest of the project: no money movement is enabled by any account action.

## Identity verification: KYC/KYB linked from registration data (prototype)

Step 2 of the customer flow starts from the signed-in account. Registration data prefills verification so the customer never retypes their email, country, phone or date of birth. Bridge onboarding (hosted ToS → customer → hosted KYC) can only start after StableX compliance is approved.

### How verification is chosen

`GET /api/auth/session` returns:

- `complianceSubjectType` — `INDIVIDUAL` for PERSONAL accounts (KYC), `BUSINESS` for BUSINESS accounts (KYB)
- `compliancePrefill` — subject fields built from stored registration data
- `providerPrefill.vove` / `providerPrefill.bridge` — what VOVE KYC/KYB and Bridge customer creation can draw from the account
- `complianceOptions.mode` — `VOVE_HOSTED` (real hosted sessions, when `VOVE_API_KEY`/`VOVE_PUBLIC_KEY` are configured), `LOCAL_SIMULATOR` (labeled simulator, when `COMPLIANCE_SIM_AUTO_APPROVE=true`), or `NOT_AVAILABLE`
- `complianceGate` — `APPROVED`, `PENDING`, `REJECTED` or `NOT_SUBMITTED`; transfers are blocked until approved

### API

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/compliance/cases/self` | Signed-in account starts its KYC/KYB case; subject prefilled from registration data |

The endpoint issues a real VOVE hosted verification session when credentials are configured; otherwise it creates a clearly labeled simulated case for local testing. Completing the hosted flow does not by itself approve the account — final approval comes from VOVE results and/or an authorized StableX decision.

### VOVE integration notes (fixed in this milestone)

- **KYB calls use the unversioned root** (`POST {root}/kyb/case`, accepting only `refId` + optional `flow`, per VOVE's docs), while KYC keeps `{base}/v2/sessions`. The previous code called KYB under `/v2/kyb/case`, which VOVE rejects as 404.
- **Hosted links use the Sandbox host** (`web.voveid.net` with `environment=Sandbox`), matching VOVE's hosted-link convention; production links use `web.voveid.com`.
- You do not need to touch either integration to run the flow locally — with `COMPLIANCE_SIM_AUTO_APPROVE=true` (already in `.env.example`) the simulator hands you an approved gate and the account becomes active immediately.
- Case statuses are refreshed via `/api/compliance/cases/:caseId/refresh` and signed VOVE webhooks at `/api/kyb/webhook`.

## Paytrie platform authorization and customer flow

StableX customers do not need to create or connect a separate Paytrie account as a standard StableX onboarding step. The current Paytrie API v2 adapter supports read-only quotes. Order creation remains fail-closed until Paytrie explicitly approves StableX's platform/partner arrangement in writing.

Keep `PAYTRIE_PLATFORM_EXECUTION_APPROVED=false`. A Paytrie API key or a retail customer's Paytrie JWT does not establish platform authorization. Do not ask StableX customers to register with Paytrie or enter Paytrie credentials as a workaround for the unresolved MSB/platform authorization issue.

The customer-specific Paytrie login endpoints are not part of the normal StableX onboarding flow and must not be linked as a required customer step. Revisit the execution authentication model only after Paytrie confirms in writing how an approved platform should authenticate and transact for its end users.
